I test the systems that don't give the same answer twice.

Three years of automating tests across UI, API and data layers — and, more recently, across AI agents, where the thing under test is allowed to phrase its answer differently every run and still be correct.

Most of my work is Python: Cucumber scenarios in Gherkin, Selenium and Playwright for the browser, SQL for everything the interface won't tell you. The AI side started when a conversational assistant on my project began shipping every two weeks and nobody could answer the only question that mattered — did anything get worse? Manual review of the evaluation export took a day and still missed regressions in the quieter intents.

So I stopped diffing spreadsheets and built a gate. That is roughly how everything below started: a review that took too long, or a defect that walked between two green suites.

Projects

Five tools, each one built after something got through

Every repo runs its own suite with no external service, so the first thing you can do is clone it and watch it go green. Two of them fail on purpose out of the box — the bundled example data contains a real regression, because a tool that catches nothing on its demo proves nothing.

  • PASS10 tests

    driftguard

    Release-gate regression testing for chatbot responses. Scores an evaluation export against an approved baseline, per intent, and fails the build when a release deviates past a threshold the product owner signed off on.

    caught — two answers that quietly became refusals between releases, in an intent nobody was watching.

    • Python
    • JSONL evaluation
    • Azure DevOps
  • PASS18 tests

    mcp-contract-tests

    A pytest plugin that pins an MCP server's tool contract and tests the paths nobody writes happy-path tests for: timeouts, malformed payloads, and a tool that errors instead of returning. Schema drift is classified as breaking or not, and shows up as a diff in the pull request.

    caught — a new required field upstream. The agent silently stopped calling the tool and answered from memory instead.

    • pytest
    • MCP
    • fault injection
    • snapshot testing
  • PASS54 steps

    bdd-fullstack-suite

    One Gherkin scenario asserting across the browser, the API and PostgreSQL. Seeding happens through the API and never through the UI, every scenario owns its data, and “exactly one row landed in the ledger” is a one-line step.

    caught — a double-submit. The UI test asserted the banner, the API test asserted 202, nobody asserted the row count.

    • behave
    • Cucumber
    • Playwright
    • psycopg
  • PASS21 tests

    dataguard-sql

    Data checks a QA engineer can own: each one a few lines of YAML, run as a release gate, reported as JUnit so a bad row appears in the same test report as a failing scenario. Stored procedures are exercised inside a transaction that is always rolled back.

    caught — an orphaned refund and a duplicate row from a retried job. Neither was an application bug; both were reported as one.

    • PostgreSQL
    • stored procedures
    • YAML
    • JUnit
  • PASS20 tests

    story2gherkin

    Drafts Gherkin from a user story, then does the part that actually matters: drops scenarios the suite already covers, explains why in plain numbers, and prints a traceability matrix so an uncovered acceptance criterion is visible instead of assumed. Nothing it writes is committed automatically.

    refused — a criterion that said “outside business hours” without defining the timezone. It asked rather than inventing one.

    • Python
    • LLM drafting
    • deduplication
    • traceability
